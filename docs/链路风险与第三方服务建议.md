# AtlasWorks 链路风险与第三方服务建议

## 当前链路

- 控制面 API：接收请求、校验参数、创建任务、入队。
- 切片 worker：按类型拆为 vector、raster、terrain、3dtiles，分别领取自己的 jobType。
- 发布服务：管理发布记录，提供 `/published`、`/publication-assets`、`/wmts` 静态访问。
- 数据库：PostgreSQL 保存任务、事件、产物、发布记录。
- 文件系统：`D:/TIF` 作为数据源，`D:/tiles` 作为瓦片/产物目录。

## 已知风险

1. 任务进度不均匀
   - 矢量任务已有导入、生成、完成阶段进度。
   - 栅格 indexedTiles 已在批处理完成时写入中间进度，但网格索引、源数据预处理、NoData 清理这些阶段仍是阶段型进度，不是逐像素精确进度。
   - 3D Tiles 对点云、OBJ、OSGB 这类外部转换命令只能按阶段估算，真实转换期间可能停在 25%。
   - 地形任务按文件数更新，多文件时较合理，单个大文件仍可能长时间无细粒度进度。

2. 队列和任务状态
   - 已改为 worker 执行并同步数据库，但停止任务目前主要是状态标记；部分外部命令未必能立即中断。
   - worker 重启会把 running 任务标记为 interrupted，不会自动断点续跑。
   - 同一个输出目录重复提交时，不同任务之间仍可能互相覆盖，需要继续强化 outputPath 锁。

3. 发布服务
   - 当前发布以静态文件和轻量 WMTS 为主，不是完整 OGC 服务引擎。
   - WMTS 能返回能力文档和瓦片，但不等价于 GeoServer/MapProxy 的完整样式、图层、权限、缓存策略。
   - 矢量 MVT/PBF 只是静态瓦片发布，样式 JSON、字体 glyph、sprite、Mapbox Style 还需要进一步补齐。

4. 数据库与部署
   - 外部数据库版依赖宿主机 PostgreSQL 可达。
   - 内置 PG15 版数据在 `./runtime/postgres15`，迁移机器时要一起备份。
   - 首次初始化应由 API 完成，worker 已跳过建表，避免多容器并发 DDL 死锁。

5. 资源隔离
   - 栅格、地形、3D Tiles 都是重任务，目前只按容器资源限制隔离。
   - 还缺少统一的任务并发配额、磁盘空间预检查、临时目录清理策略。

## 建议优先补的功能

1. 进度事件标准化
   - 给所有 worker 增加统一 `updateTaskProgress(taskId, progress, stage, message)` helper。
   - 栅格批处理每完成一批同步一次数据库。
   - 3D Tiles 外部命令至少按输入文件、阶段和输出文件数量估算进度。

2. 输出目录锁
   - 入队前锁定 outputPath。
   - 任务结束、失败、停止后释放。
   - 禁止两个 running/queued 任务写同一个目录。

3. 停止任务
   - worker 侧轮询 stop 标记。
   - 外部命令使用 process group，停止时杀掉子进程树。

4. 发布能力分层
   - 静态发布继续保留，适合 XYZ/TMS/MVT/GeoJSON/3D Tiles/Cesium Terrain。
   - 标准 OGC 服务建议接第三方服务，不建议全部手写。

## 第三方服务集成建议

### 发布服务

- GeoServer：适合 WMS/WFS/WCS、样式 SLD、PostGIS 图层、复杂 OGC 发布。
- MapProxy：适合 WMTS/WMS 缓存代理、瓦片缓存、坐标系适配。
- TiTiler：适合 COG/GeoTIFF 动态瓦片和范围查询。
- pg_tileserv：适合 PostGIS 动态 MVT。
- Martin：适合 PostGIS/MBTiles/PMTiles 的 MVT 发布。
- tileserver-gl：适合 MBTiles 矢量瓦片和 Mapbox Style 预览。
- nginx：适合纯静态瓦片、3D Tiles、Cesium Terrain 高性能分发。

### 切片/转换

- tippecanoe：GeoJSON/SHP 转 MBTiles/MVT，适合二维矢量金字塔。
- ogr2ogr/GDAL：矢量格式转换、投影转换、数据清洗。
- gdal2tiles/rio-tiler：栅格瓦片生产。
- cesium-terrain-builder：地形 terrain 生产，当前已有。
- py3dtiles：点云 3D Tiles，当前已有依赖。
- obj2gltf / osgconv：模型转换，当前已有依赖。

## 推荐路线

1. 短期：继续保留当前静态发布能力，补齐进度、停止、输出锁。
2. 中期：引入 nginx 作为静态发布前端，publisher 只管记录和地址生成。
3. 中期：引入 Martin 或 tileserver-gl 处理 MBTiles/PMTiles/MVT 发布。
4. 长期：需要 WMS/WFS/WCS 时接 GeoServer，不建议在当前 Flask 服务里重写完整 OGC 服务。
